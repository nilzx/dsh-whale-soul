# 明确的对话约定

[English](agreements.md)

桥接只处理一组明确的中英文未来约定表达，把实际用户消息、Agent接受动作和支持的交付结果接入现有约定存储。普通承诺、事实保存要求和一次性任务指令，不会自动升级成双方约定。

## 提议与接受

1. 用户明确提出条款，例如：“我们约定：以后讨论方案时，先给结论再补理由。”此时创建`proposed`，不默认任何一方已经接受。
2. Agent依据自身人格和能力判断是否接受。需要接受时，用当前提议的record ID及修订号执行`soul_agreement_accept`，这只代表Agent一方接受。
3. 用户另行确认，例如：“我接受这个约定。”两方接受都已记录才成为`open`；提议后的两个接受动作可以任意先后。

接受工具只传已有目标和版本：

```json
{"record_id":"offered-record-id","expected_revision":1}
```

应使用当前提议提供的实际值；版本变化后重新查看，目标含混则保持未决。Agent在普通回复里说“好的”不等于已记录接受。回复应按真实提交状态描述，提议阶段不能称为“已经说好了”。

只有仍在有效期内的open约定作为现行约定记忆加载。待接受提议另外带状态提供给当前对话；提议和接受均不增加成长或成熟度资格。

## 取消、期限与履行

用户明确说“取消这个约定”等，可关闭被定位的当前约定。存在多个可能目标时，需要明确条款，不替用户猜选。识别到的期限会关闭接受及现行记忆窗口；到期不等于履行。

桥接不会根据普通工具成功、Agent说“做完了”或会话空闲推断履行。未知自由文本交付仍保持open；条款提到未来时间，也不自动建立后台任务。

## 待办状态交付适配器

首个交付适配器核验状态更新，不核验待办背后的任意工作。先有一项未完成待办，再明确提议，例如：“我们约定：下次把待办「整理读书笔记」标记为完成。”双方接受后，实际成功的`todo_write`结果须在原Session将同一连续目标从`pending`或`in_progress`改为`completed`，这一约定才成为`fulfilled`。

提议唯一指向未完成目标时，宿主绑定可选元数据：

```json
{"kind":"todo","session_id":"original-session","content":"整理读书笔记","origin_seq":12}
```

字段来自真实Session快照，模型不提交“已履行”标志。工具失败、另一项待办、另一Session、移除后重新加入，或者口头说完成，都不能满足这项绑定。只说“完成待办X”不足以证明背后的工作，也不会获得这一状态交付绑定。迟到的可核验状态交付可将expired约定转为fulfilled，过期修订仍保留在历史中。

状态变化、目标绑定和来源保存在元数据，记忆正文表达条款，不夹带操作回执或诊断。广泛自然语言覆盖及其他具体产物的交付适配器作为独立扩展；窄检查不代表所有模型或Web生命周期都已覆盖。
